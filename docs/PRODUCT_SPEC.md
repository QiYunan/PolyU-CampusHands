# CampusHands 产品规格

## 用户与问题

CampusHands 面向 PolyU 学生。学生在校园内临时需要物品或帮助时，公开社交帖子常因曝光不稳定、响应慢、地点不相关而难以在截止时间前完成求助。产品以校内、地点和时限为约束，帮助求助者联系可用的同学并跟踪交接结果。

首个场景 **BorrowLoop** 聚焦紧急借用物品：科学计算器、充电器、转接头、文具和雨伞。现场协助、短时技能帮助及其他校园互助留待后续产品扩展；图片识别、地图/GPS、真实校方认证、外部通知、移动 App 和多校支持不属于当前五个里程碑。

## 用户能做什么

- **Requester**：描述所需物品、地点和截止时间；回答必要的澄清问题；查看求助状态、公开的操作时间线和匹配后的交接信息；取消请求并确认交接完成。
- **Helper**：在站内 Inbox 查看与自己相关的借用邀请及物品、地点、时限；接受或拒绝；在交接后确认完成。
- **演示者**：在明确标注的 Demo Mode 中切换 Alice、Bob、Carol 等虚构角色，演示一次拒绝后联系下一位帮助者的流程。演示数据不使用真实学生资料。

一次完整 BorrowLoop 的目标体验：Alice 提出“我 20 分钟后在 VA 考试，但计算器坏了，想借一部科学计算器”；系统取得必要字段、寻找候选人并联系 Bob；Bob 拒绝或超时后联系 Carol；Carol 接受；Alice 看到匹配和交接信息；双方确认后请求完成。公开时间线只显示类似“已解析请求”“已联系 Bob”“Bob 已拒绝”“Carol 已接受”的可理解事件，不展示内部推理。

在 BorrowLoop 的确定性流程中，请求先保存为草稿，Requester 再明确开始匹配。“最晚需要时间”限制寻找帮助者；匹配成功后可继续交接，直到双方确认完成或 Requester 取消。取消已匹配请求会释放预留物品，完成交接后物品保持不可用，归还流程不在本阶段范围内。

## 阶段范围

**第一阶段仅验证前端 → 后端 → 数据库 → 前端的基础闭环。** 用户通过结构化表单创建一条借物请求，刷新或重新打开页面后仍能读取同一记录。此阶段不接入真实 LLM，也不要求自然语言解析、候选人匹配、Helper Inbox 或 WebSocket。详见 [里程碑 01](milestones/01-mvp-foundation.md)。

后续依次交付确定性的 BorrowLoop 匹配和交接、Agent 与模型接入、实时更新、演示与协作加固；以 [里程碑目录](milestones/02-borrowloop-flow.md)及 [验收场景](ACCEPTANCE_TESTS.md)为阶段边界。最终课程演示需可交互、展示有意义的对话与 Agent 行为，并能在五分钟内可靠完成。

## 体验原则

- 优先呈现当前状态、下一步可做的动作和截止时间；移动端基本可用。
- 候选人与结果来自实际演示数据；不向用户暗示尚未发生的接受、交接或完成。
- 内部匹配字段不形成公开用户排名。
- 产品文案与技术实现的职责分界见 [架构](ARCHITECTURE.md)和 [Agent 工作流](AGENT_WORKFLOW.md)。
